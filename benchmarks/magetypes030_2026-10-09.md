# magetypes 0.9.30 constructor qualification — 2026-10-09

The analyzer compiled against magetypes 0.9.30 emitted deprecated-constructor
warnings that CI denies with `-D warnings`. The migration changes constructor
names to their token-taking `_t` forms, retaining the existing token and arguments.
Exact feature dumps match before and after at all three measured dispatch tiers.

Baseline: `e6c72f99390c190c102275c3b0e4d41fe0a734a4`.
Local jj change: `qoulunrxzpowrkoyqlvnymzkurxvmqxt` (one local commit; no push).
The external commit receipt records its final SHA.

API/source review used local archmage commit
`e2dbab66ef5aa08f8e23ed05248e7d1217f58475`: its README, CHANGELOG,
`docs/TOKEN-CONSTRUCTOR-MIGRATION.md` and
`magetypes/src/simd/generic/generated/f32x8_impl.rs`. The deprecated forwarders
call the `_t` constructors with the same token and argument order. The manifest
now requires magetypes 0.9.30 so an older constructor API cannot satisfy it.
The tested lockfile resolves archmage, archmage-macros and magetypes to 0.9.30.

`mechanical-proof.json` checks all six files: reversing only the constructor
renames and normalizing whitespace reproduces the baseline source exactly.
No arithmetic, SIMD width, token acquisition or lint policy changes occur in
those files. No `allow(deprecated)` was added. zenpredict sources and the
`feat/znpr-v4-graph` bookmark were left unchanged.

## Exact output oracle

A test-only opt-in dump in the existing `golden_is_stable` test reuses its
26 synthetic images, gamma/linear configurations and 117 supported features.
The images cover RGB8, RGBA8, u16, f32, PQ, HLG, wide gamut and premultiplied alpha.
Every available feature value is serialized by type; f32 uses its raw bits,
including NaN payloads and signed zero. Each dump contains 6,072 values.

Each forced tier ran in a fresh process with only this test and one test thread.
The `_dev` dispatch control asserts that the requested tier is available and
that higher tiers are disabled. The hook writes the dump before running the
original golden assertions. It does not bless or bypass them.

Both before/after v4 and v3 dumps have SHA256
`dcc467374ba76336012ed867aeb6b0940968a985b62a1837fc92587e9700055a`.
Both scalar dumps have SHA256
`1840308cbbc9276f1c7978b70a0d13e7800b88832b36341d4b49bb5362ccc269`.
`cmp` accepts each before/after pair. A one-bit mutation in the first f32 value

Forced scalar already fails the unchanged golden tolerance on
`patch_fraction[16]`, `chroma_luma_covariance_cb[3]`,
`chroma_luma_covariance_cr[3]` and `spectral_slope_y[9]` before this migration.
The post-migration dump is byte-identical and fails those same four cases.
No golden or expectation was changed. This remains an open baseline issue,
recorded in CLAUDE.md. This qualification asserts within-tier before/after
identity; it does not assert identity between scalar and SIMD. ARM and WASM
outputs were not measured here.
