# `analyze_features` performance — size × content sweep, 2026-08-28

Host: Apple aarch64 laptop, 12 cores, macOS. Release profile (`lto = "thin"`,
`codegen-units = 1`), **no `-C target-cpu=native`** — runtime SIMD dispatch is
what ships. Every cargo command ran under `nice -n 19 … -j 4`.

Harness: `examples/per_feature_cost_grid.rs` with `PFC_BASELINE_ONLY=1`
(`just perf-grid`), which times `analyze_features(FeatureSet::SUPPORTED)` —
117 features, the `hdr` build — over real codec-corpus content. Median of
≥ 5 runs and ≥ 100 ms per cell, 3 distinct crops per cell, median over crops.

Content (no synthetic gradients): `photo` = CID22 512² centre crops at 64/256
and clic2025 1024² crops above; `photohard` = gb82, photography selected to
resist metric gaming; `screen` = gb82-sc, screenshots / UI / anti-aliased text;
`mixed` = a photo/screen checkerboard of tiles. Sizes larger than a source
mosaic distinct crops (2×2 … 8×8).

> **The `screen` class changed source in this commit range.** It used to read
> `gb82`, which is the *photographic* set — so every photo-vs-screen split this
> grid produced before 2026-08-28, including
> `per_feature_cost_grid_2026-08-28.tsv` and the "Cost vs use" table in
> `docs/feature-consumption.md` that consumes it, was photo-vs-photo. The
> screen-content set is `gb82-sc`. `gb82` is still measured, correctly named
> `photohard`.
>
> **No line-art class.** The only line-art-ish sources in the local checkout
> (`gb82-sc/graph.png` 796×481, `windows95.png` 640×480) are below the 512 tile
> floor, and `imazen-26` is manifest-only here. Line art appears inside `screen`
> as text and UI content; no conclusion about line art should be drawn from

Raw rows: [`perf_2026-08-28.tsv`](perf_2026-08-28.tsv).

The two positive cells (`photo 64` +0.21 %, `screen 256` +3.02 %) are inside

those sizes the honest statement is "no measurable change", not a regression —
which is what the shape of both changes predicts, since each removes a cost
proportional to image height.

**Content note, now that `screen` really is screen content:** it is the
*slowest* class per pixel at 1024² and above (5.78 vs 5.45 ns/px at 1024²), and
the one that gained most (1.35×). Sharp edges and flat regions push more work
through the histogram and palette passes than photographic noise does. Under
the old mislabeled grid this was invisible — both "classes" were photos.

## The fitted intercept is an artifact; the real per-call floor is ~0.6 ms

Fitting `total_ns = α + β·pixels` over all five sides gives α ≈ 2.7 ms,
β ≈ 0.98 ns/px (before) — the number quoted in `docs/dispatch-axes.md`. **That
α is not a per-call floor.** The measured 64² call is 0.63 ms, four times
smaller than the "intercept". The fit is dominated by the two largest sides and
the cost is not affine in pixels: sampling budgets (`DEFAULT_PIXEL_BUDGET`,
`hf_max_blocks`, the palette and XYB block strides) cap several passes, so
marginal cost per pixel falls by a factor of 26 across the sweep.

Marginal ns/px between adjacent sides, after:

| class | 64→256 | 256→1024 | 1024→2048 | 2048→4096 |
|---|--:|--:|--:|--:|
| photo | 16.22 | 4.15 | 0.68 | 0.62 |
| photohard | 16.17 | 4.20 | 0.67 | 0.62 |
| screen | 16.41 | 4.60 | 0.68 | 0.61 |
| mixed | 16.25 | 4.13 | 0.75 | 0.62 |

Read it as: a genuine fixed cost near **0.5–0.6 ms**, a steep sampled-but-not-
yet-capped region up to ~1 MP, and an asymptote near **0.62 ns/px** above 4 MP.
Quoting a single α + β pair over the whole range mis-states both ends. Anyone
budgeting per-call analysis below ~1 MP should use the measured cell, not the
fit.

## What was optimized

Both changes are **byte-identical in output**, verified by the byte-exact lock
`just bitlock` (3,740 values over 16 fixtures, `f32::to_bits()` comparison)
plus the 226-test lib suite including `versioning::golden_is_stable`.

1. **`tier3::luma_histogram_stats` — four interleaved bin arrays** (`103c5b1b`).
   The histogram is the one content pass that is not budget-capped: it walks
   every row and every 4th pixel, so its share grows with image size. Its
   `bins[b] += 1` serialized on store-to-load forwarding, since neighbouring
   pixels have neighbouring luma. Four independent arrays summed at the end are
   exact for u32 counts. Alone: −7.9 % at photo 2048², −14.6 % at photo 4096²,
   −22.6 % at screen 4096².
2. **`xyb_color_loss::xyb_bquarter_chroma_loss_from_stream` — borrow the 2-row
   window instead of copying it** (`cca3c625`). It copied 2 full rows per
   block-row to read four pixels out of a handful of blocks — ~50 MB memmoved
   per call at 4096² to sample ~1.5 KB. New `RowStream::try_borrow_row(&self)`
   hands out `Inner::Native` rows zero-copy, and the `&self` receiver is what
   lets two rows be held at once. Alone: −4.7 % at photo 2048² and 4096².

## Negative result: vectorizing the chroma-subsample DCT bought nothing

`chroma_subsample_loss::{fdct2d, idct2d}` were naive scalar 8×8×8 matrix
multiplies and looked like the obvious target — 14 % of the 64² profile. They
were rewritten as `#[magetypes]` f32x8 kernels with the free index in the lanes
(bit-identical by construction: same reduction order per output, no `mul_add`,
accumulator started at `zero()` so `0.0 + −0.0` keeps its sign), verified
byte-identical across all 25 archmage token permutations against a
test-owned scalar reference.

**Measured end-to-end effect: 0.0 % at every one of 20 cells** (interleaved
A/B, 3 repetitions; the largest deviation either way was 0.39 %). On aarch64
NEON is baseline, so LLVM had already vectorized the scalar loops into
equivalent code — the same caveat `benches/tier_kernels.rs` documents. The
change was reverted rather than landed: it added a SIMD kernel, an
architecture-specific test and a `pub(crate)` export for no measured win on the
host that could measure it. Recorded here so the next session does not repeat
it. It may still help SSE-only x86 or wasm128, which this host cannot measure;
that would need a measurement on such a host before it is worth landing.

## Not attempted, with reasons

- **`palette::scan_palette` (44 % at 4096²)** — the per-pixel work is
  3 loads + 3 shifts + 2 ors + a scattered byte store into a 32 KiB table, and
  the measured ~1.6 cycles/px says it is already issue-bound rather than
  stalled. Making it faster means computing the bin indices SIMD-wide and
  scattering scalar, which needs an RGB8 deinterleave; worth doing, but it is
  its own measured change.
- **`tier3::dct_stats` 8-row band copy** — **attempted, measured, reverted.**
  It is the largest single memmove source (474 samples at 4096²), so it looked
  like the XYB fix again: add `ChunkInput::try_borrow_row` (u8 answers via
  `RowStream::try_borrow_row`, f32 always declines) and hold the band as
  `[&[R]; 8]` instead of copying it. Bit-exact, 226 tests green, bitlock clean.
  Measured over 19 interleaved samples per arm it wins ~1.7–3.5 % at 2048² in
  all four classes but only 0.0–2.1 % at 4096², and it **regresses `photohard`
  by a consistent +1.2 / +1.5 / +1.5 % at 64² / 256² / 1024²** (within-arm
  spread on those cells is only 3.3–4.5 %, so the sign is real even though the
  magnitude is small). The likely cause is locality: the copied band is one hot
  8-row buffer that was just written, while eight borrowed rows of a large
  image are eight distant regions, and at small sizes the copy it removes was
  nearly free. Reverted under the "no regression at any size" rule. A version
  that borrows only when the band is large enough to pay would probably clear
  the bar, but that is a threshold to measure, not to guess.
- **`chroma_subsample_dct_loss_from_stream` 8-row band copy** — same pattern,
  same reasoning.
- **Quantize-step vectorization** in the chroma-subsample kernel (the `/q`,
  `.round()`, `*q` triple, plausibly ~45 % of that kernel) — blocked on
  rounding semantics: `magetypes`' vector `round` is ties-to-even
  (`vrndnq_f32`), Rust's `f32::round()` is ties-away-from-zero. Using it would
  move values on any coefficient landing exactly on .5. Needs a
  `roundTiesAway` vector primitive upstream in magetypes before it can be
  bit-exact.

## Reproducing

```bash
just bitlock-bless                   # before touching a kernel
just perf-grid ~/tmp/before.tsv      # baseline
# …change…
just bitlock                         # must stay byte-identical
just perf-grid ~/tmp/after.tsv
```

The A/B in this document alternated two prebuilt binaries rather than
re-running the same one twice, so that machine drift cannot be mistaken for a
win.
