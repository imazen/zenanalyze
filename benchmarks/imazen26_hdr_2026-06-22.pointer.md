## What changed vs 2026-06-14 — and why it's MORE than SDR (validated, explained)

Unlike the SDR re-extraction (7 features changed), the HDR parquets show **53
(native) / 69 (grid)** features changed, some large (`edge_slope_stdev` 40 %,
`luma_kurtosis` 23–35 %, `variance` 12 %). This is **not a bug** — it's the sum of
TWO independent, legitimate changes the 2026-06-14 baseline predates:

1. **This cycle's feature-determinism work** (the same 7 as SDR:
   `edge_slope_stdev`, `variance`, `chroma_complexity`,
   `chroma_luma_covariance_{cb,cr}`, `spectral_slope_y`, `colourfulness`) —
   **amplified on HDR's wide dynamic range** (the cancellation-prone moments —
   variance, kurtosis — swing far more on PQ-range data than on 8-bit SDR), plus
   the depth-tier EOTF (`peak_luminance_nits` / `hdr_headroom_stops` /
   `wide_gamut_peak`, commit c596d15).
2. **`zenpixels-convert` 0.2.11 → 0.2.14** (commit `ee38c55`, **2026-06-18** —
   after the HDR baseline, before this cycle): *"honor signaled diffuse_white"*.
   The HDR PQ-16 → RGB8 **narrowing** for the tier1/2/3 path goes through
   `zenpixels_convert::RowConverter`, so this white-point change shifted the
   narrowed input pixels → **every tier1/2/3 feature on HDR moved** (kurtosis,
   laplacian, sharpness, aq_map, noise_floor, …). SDR never hits the converter
   (already RGB8), which is exactly why SDR showed *only* the 7 feature-math
   changes and HDR shows ~50 more.

Diagnosis trail: `luma_kurtosis` (not touched by `fixed_reduce8`/`rsqrt`) changed
on HDR but not SDR → the only SDR↔HDR difference is the narrowing → traced to the
`zenpixels-convert` bump via `git show a6526690:Cargo.toml` (0.2.11 at baseline).

**The new extraction is the correct current-state** (current code + the 0.2.14
diffuse_white handling). **Downstream:** any HDR model trained on the 2026-06-14
HDR features is stale on a broad set of columns — retrain against this artifact.
